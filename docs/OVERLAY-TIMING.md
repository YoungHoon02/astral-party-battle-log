# 오버레이 연출 동기화

서버 패킷은 게임 연출보다 먼저 도착한다. 그대로 찍으면 타격이 화면에 나오기도 전에
오버레이가 결과를 보여준다. 이 문서는 **해석한 결과를 연출이 끝날 때까지 화면에서만
숨기는** 구조와, 그 지연값을 재는 방법을 적는다.

> **현재 상태: PK(공격·타격)만 측정했다.** 나머지 종류는 0이라 받은 순서만 지키고 바로
> 보여준다. 아래 [측정 현황](#측정-현황)을 볼 것.

## 원칙

**늦추는 것은 오버레이 출력뿐이다.**

```
패킷 수신 → 프레임 재조립 → 즉시 해석 → 로거 상태 즉시 갱신 → 줄 생성
    ├─ battle-log.txt : 지금 기록 (시각·순서 그대로)
    └─ OverlaySchedule : 예약 → 연출 시점에 LogOverlay로
```

해석이나 상태 갱신을 늦추면 안 되는 이유:

- 턴 주인·원인 문맥(`_turnOwner`, `_said*`)이 다음 패킷과 뒤섞인다
- 골드 송금 짝 맞추기(600ms 보류)가 깨진다
- 소켓 스레드가 기다리게 된다

600ms 골드 보류는 **문장을 만들기 위한 것**이고 표시 예약은 **화면에 내보내기 위한
것**이다. 섞지 않는다 — 보류됐던 줄은 원래 패킷의 종류·그룹을 들고 예약 큐에 들어간다.

### 예전에 뺀 "턴 경계까지 모아 보내기"와 다르다

v1.20.0에서 들어낸 장치는 턴이 끝날 때까지 줄을 모았다가 한꺼번에 내보냈다. 자기 턴
내내 화면이 비어서 너무 늦었다. 이번 구조는 **사건마다** 그 사건의 연출 시간만큼만
기다린다.

## 구성

| 위치 | 역할 |
| --- | --- |
| `Log/LineKind.cs` | 사건 종류 |
| `Log/BattleLogger.cs` | 패킷마다 종류·그룹을 정하고 줄에 붙여 넘긴다 |
| `UI/OverlaySchedule.cs` | 예약 큐. Unity에 의존하지 않는다 |
| `UI/FramePump.cs` | 매 프레임 시계·배속을 넘기고 기한이 된 줄을 꺼낸다 |
| `UI/LogOverlay.cs` | 기존 그대로 그린다 |

소켓 스레드는 `OverlaySchedule.Line/Page/Reset`으로 넣기만 한다. Unity 객체에 손대지
않고, 기다리지 않고, 디스크에 쓰지 않는다.

### 파일 기록도 소켓 스레드에서 뺐다

전에는 `BattleLogger`가 줄마다 소켓 스레드에서 `File.AppendAllText`를 불렀다. 디스크가
잠깐 막히면 그만큼 다음 패킷 처리가 밀린다(AnimSpeedMod에서 설정 파일 쓰기가 최악 46ms를
막은 기록이 있다). 이제 `Log/LogFileWriter.cs`의 전용 스레드가 쓴다.

- **시각은 넣을 때 찍는다.** 해석 시점의 `HH:mm:ss.fff`라 파일 내용·순서·시각은 전과 같다.
- 새 판의 파일 비우기도 같은 큐를 타서 줄과 순서가 섞이지 않는다.
- 큐(2만 줄)가 차면 그 줄은 버리고 경고를 한 번 남긴다 — 소켓 스레드를 막지 않는 쪽을 골랐다.
- 플러그인 언로드와 프로세스 종료(`AppDomain.ProcessExit`, 순수 .NET 이벤트)에서 남은 줄을
  최대 1초 기다려 쓴다.

## 시계

**프레임 시계**를 쓴다. 매 프레임 `Time.unscaledDeltaTime`을 더하되
`Time.maximumDeltaTime`으로 자른다.

- 게임 연출은 Unity가 잘라낸 `deltaTime`으로 진행한다. 3초 끊김이 있어도 연출은
  0.333초만 나아간다. 실시간 시계를 쓰면 끊김 뒤에 로그가 연출보다 먼저 한꺼번에 풀린다.
- 창이 멈춰 프레임이 안 돌면 시계도 멈춘다. 연출도 멈추므로 맞다.
- Unity 값을 못 읽으면 `Stopwatch`로 대신 흐른다. 시계가 멈추면 로그가 영영 안 나오므로
  배속 연동 실패가 전투 로그 실패로 번지지 않게 한다.

수신 시각은 소켓 스레드가 이 시계를 `Volatile.Read`로 읽어 찍는다. 해상도는 한 프레임이다.

## 배속

**`Time.timeScale`을 읽는다.** AnimSpeedMod(`AstralPartyAnimSpeedMod/Plugin.cs`
`OnFrameTick`)가 배속을 바로 이 값에 쓴다:

```csharp
if (SpeedsDiffer(Time.timeScale, target)) Time.timeScale = target;
```

그래서 다른 모드의 내부 필드를 리플렉션할 필요가 없다. 모드가 없으면 1이고, 배속 제외
씬에서는 AnimSpeedMod가 1로 되돌린다. **게임 자체의 방 속도 설정은 이 값에 드러나지
않는다** — [알려진 한계](#알려진-한계).

- `Time.deltaTime`에서 역산하지 않는다 — 프레임 저하와 배속을 구분할 수 없다.
- 유한하고 0.25~10 사이가 아니면 1로 본다. 이 범위는 측정값이 아니라 안전장치다
  (AnimSpeedMod 배속 목록은 1·1.5·2·3·5). 게임 자체 연출도 `timeScale`을 바꿀 수 있다.
- **줄을 넣을 때의 배속**으로 기한을 정하고, 기다리는 도중 배속이 바뀌어도 다시
  계산하지 않는다. 새로 들어오는 사건부터 새 배속이 적용된다.

## 기한 계산

```
기한 = 수신 시각 + 지연(종류) / 배속 + 보정값
```

세 가지로 보정한다.

1. **같은 그룹은 첫 줄의 기한을 쓴다.** 그룹 = 패킷 하나. 머리줄과 효과 줄이
   흩어지지 않는다.
2. **앞 줄의 기한보다 이르지 않다.** 지연이 짧은 종류가 긴 종류를 추월하면 로그 순서가
   뒤집힌다.
3. **수신 뒤 `SyncMaxDelayMs`를 넘지 않는다.** 앞 줄 하나가 길게 밀려도 뒤 줄이
   무한정 끌려가지 않는다.

꺼낼 때는 **받은 순서(FIFO)** 로, 맨 앞 줄의 기한이 됐을 때만 꺼낸다. 3번 때문에 기한이
앞 줄보다 이른 줄이 생겨도 화면 순서는 그대로다.

대기열이 4096줄을 넘으면 기한을 무시하고 오래된 것부터 내보낸다(버리지 않는다).
메모리 안전장치다.

## 초기화

각 줄은 넣을 때의 **세대**를 들고 있고, 꺼낼 때 현재 세대와 다르면 버린다. 큐를 비우는
것만으로는 이미 꺼내 둔 줄이 경쟁 상태로 남을 수 있어서다.

| 상황 | 호출 | 동작 |
| --- | --- | --- |
| 새 판(StartGame / MatchSuccess / SingleCampaign / 방 변경) | `Reset` | 세대 증가 + **비우기 신호도 큐를 태운다** |
| 전투 씬 이탈 | `Discard` | 세대 증가. 화면은 그대로 — 이미 보인 로그는 결과 화면에서도 볼 수 있다 |
| 플러그인 언로드 | `Discard` | |
| 오버레이 꺼짐(`Overlay.Enabled=false`) | — | 예약 큐에 아무것도 넣지 않는다 |

`Reset`의 비우기를 큐에 태우는 이유: 따로 보내면 메인 스레드가 이미 꺼낸 지난 판 줄이
비우기 **뒤에** 오버레이에 도착할 수 있다. 큐를 타면 FIFO라 지난 판 줄은 항상 비우기
앞에 선다.

**비우기 신호만은 세대가 지나도 버리지 않는다.** 새 판 직후 전투 이탈(`Discard`)이 겹치면
비우기의 세대가 곧바로 낡는데, 버리면 지난 판 페이지가 새 판에 남는다. 비우기는 여러 번
실행돼도 무해하다.

## 설정

`BepInEx/config/astralparty.battlelog.cfg`

| | 기본값 | |
| --- | --- | --- |
| `Overlay.SyncWithAnimation` | true | 끄면 지연 없이 받은 순서대로 |
| `Overlay.SyncOffsetMs` | 0 | 모든 지연에 더하는 보정. 음수면 일찍 |
| `Overlay.SyncMaxDelayMs` | 8000 | 수신 뒤 최대 대기. 측정값이 아니라 정지 방지 장치 |
| `Diagnostics.TraceTiming` | false | 측정 기록. 켜면 F10으로 표시 |

종류별 지연은 일반 설정에 두지 않고 **측정 프로필 파일**로 관리한다.

## 측정 프로필

`BepInEx/plugins/AstralPartyBattleLog/overlay-timing.tsv` — 없으면 모든 종류가 0이다.
플러그인이 만들지 않는다(나중 버전의 기본값을 빈 파일이 덮지 않게).

```
# 종류<TAB>밀리초[<TAB>fixed]
attack	1200
hit	900
dice	1500	fixed
```

**`fixed`** 는 배속을 따르지 않는 연출이다. 게임은 `UniTask.Delay`를 배속 적용
(`DelayType.DeltaTime`)과 미적용(`DelayType.UnscaledDeltaTime`) 두 가지로 다 쓴다
(디컴파일에서 둘 다 확인). 그래서 종류마다 배속을 따르는지 따로 재야 한다.

위 예시의 숫자는 **형식 설명용이며 측정값이 아니다.**

## 측정 현황

**측정한 값이 없다.** 확인한 것:

- **AnimSpeedMod 리포에 연출 시간 측정이 없다.** 기록된 측정은 설정 파일 읽기 지연
  (최악 46ms → 1.3ms) 하나뿐이다.
- **게임 코드에 쓸 만한 상수가 없다.** 연출 대기는 대부분 변수·에셋(타임라인) 값이다.
  `GachaDiceManager._DiceShowTime = 1000`은 **가챠** 주사위라 전투와 무관하다.
- **네트워크 계층에 순차 큐가 없다.** `RPCMsgManager.ReceiveRPCCallStatic`은 패킷마다
  `UniTaskExtensions.Forget(DealOnPushRPCMsg(...))`로 핸들러를 바로 띄운다. 연출 순서는
  각 게임 로직이 알아서 정한다.

### 재는 법

1. 설정에서 `Diagnostics.TraceTiming = true`
2. 배속 1로 한 판. 연출이 **끝나는 순간** F10을 누른다 (타격이 들어가는 순간, 말이 멈추는
   순간, 카드가 뒤집히는 순간 등)
3. `LogOutput.log`에 이런 모양으로 남는다 (숫자는 형식 예시)

   ```
   [timing] mark speed=1 attack=1184ms hit=1180ms turn=6021ms
   ```

   방금 본 연출에 해당하는 종류의 값이 그 한 번의 표본이다.
4. 종류마다 여러 번 재서 **중앙값**을 프로필에 적는다. 편차가 크면 고정 지연이 맞지
   않는 사건이므로 표에 그렇게 적는다.
5. 배속 2·3에서 다시 잰다. 값이 배속만큼 줄면 그대로, 안 줄면 `fixed`.
6. 프로필을 넣고 다시 한 판 돌리면 줄이 나갈 때마다 이런 모양으로 남는다

   ```
   [timing] show kind=attack planned=1200ms waited=1201ms speed=1
   ```

### 측정 1 — 타격 (2026-09-17, 기본 속도 방, AnimSpeedMod 1배속, 봇전)

PK 결과 패킷(`BattleS2C`)을 받은 뒤 **타격이 화면에 들어가기까지**. F10 기록을
`battle-log.txt`의 수신 시각과 맞춰 어느 PK인지 확인했다.

| # | PK (공격 → 방어) | 결과 수신 | 타격까지 | 그 사이 먼저 도착한 패킷 |
| --- | --- | --- | ---: | --- |
| 1 | 보니(사용자) → 마법 찻주전자1 | 23:07:30.259 | 4633ms | 없음 |
| 2 | 미사키(봇) → 마법 찻주전자3 | 23:07:48.149 | 4988ms | 골드, 펭 행동 시작, 펭 효과카드 |
| 3 | 펭(봇) → 마법 찻주전자2 | 23:07:59.156 | **7717ms** | 골드, 간수 행동 시작·주사위, 찻주전자1 행동 시작·주사위 |
| 4 | 마법 찻주전자1 → 보니 | 23:08:15.668 | 2958ms | 찻주전자2 행동 시작·주사위 |
| 5 | 마법 찻주전자2 → 보니 | 23:08:26.251 | 3458ms | 찻주전자3 행동 시작·주사위 |
| 6 | 마법 찻주전자3 → 파루난(봇) | 23:08:34.257 | 4900ms | 교도소장 행동 시작·주사위, 라운드 2 |

**중앙값 4767ms, 범위 2958~7717ms (약 2.6배).** 편차가 커서 고정 지연 하나로는 맞지 않는다.

편차의 주된 원인은 **캐릭터 스킨마다 공격 모션 길이가 달라서**다(플레이어 확인). 다만 같은
마법 찻주전자끼리도 4·5번(약 3초)과 6번(4.9초)이 달라, 방어자 쪽 모션이나 누른 시점의
오차도 섞인 것으로 보인다. 스킨별로 맞추려면 공격자 스킨을 읽어야 하는데, 지금은 `Hero`에서
`HeroId`만 읽는다(손패가 같은 메시지에 있어서). 스킨이 다른 안전한 필드에 있는지는 확인하지 않았다.

그리고 **타격이 보이기 전에 다음 차례의 패킷이 1초 간격으로 계속 도착했다**(4·5번 제외 전부
2~4개). 봇 차례는 서버 타이머로 오고 화면은 PK가 끝나야 넘어간다면, 이 줄들은 `turn`·`dice`
지연을 0으로 두는 한 PK 줄과 함께 풀려 **자기 연출보다 먼저** 보인다. 누적 모델이 필요한지는
측정 2(봇 차례 표시)로 확인한다.

원본: 이 측정의 `LogOutput.log`와 `battle-log.txt`는 리포에 넣지 않는다(참가자 표시명 포함).

**적용: `attack`·`hit` 모두 4767ms (중앙값).** 스킨 편차 때문에 절반쯤은 여전히 먼저 뜨는 것을
감수했다. PK 줄에도 같은 값을 거는 이유는, PK 줄만 먼저 뜨면 ATK·DICE로 피해량이 드러나기
때문이다(공격 시작 표본 433ms는 한 번뿐이라 쓰지 않았다). 배속을 따르는지는 아직 재지 않아
`fixed` 없이 둔다.

## 알려진 한계

- **"수신 시각 + 고정 지연"이 맞는 모델인지 아직 모른다.** 게임이 연출을 순서대로
  재생한다면(앞 연출이 끝나야 다음 연출 시작) 몰려 온 패킷일수록 누적으로 밀린다. 봇과
  하면 서버가 몰아서 보내므로 여기서 차이가 드러날 것이다. 측정 편차가 크면 이 가능성부터
  볼 것.
- 게임이 `timeScale`을 1보다 작게 낮추는 연출(느린 화면)이 있다면, 그 순간 들어온 줄은
  더 오래 기다린다. `SyncMaxDelayMs`에서 잘린다.
- 게임이 `timeScale = 0`으로 멈추는 일이 있으면 프레임 시계는 계속 흐르므로 그동안
  줄이 먼저 풀린다. 온라인 게임이라 없을 것으로 보지만 확인하지 않았다.
- **게임 자체의 방 속도 설정은 반영하지 않는다.** 게임은 `timeScale`을 쓰지 않고
  `Room.SpeedType`(필드 40)으로 설정표(`ChoosingTimeLimit` gamespeed)를 찾아
  `AnimSpeed`/`DiceSpeed`/`PerformSpeed`/`VfxSpeed`를 분야별로 따로 적용한다
  (`GameLogic/BattleConfig`). 빠른 방에서는 연출이 빨라지는데 여기서는 1배속으로 계산하므로
  **로그가 연출보다 늦게** 뜬다. 필요해지면 위 필드와 설정표를 읽어 종류별 배율로 곱하면
  된다 — 측정 프로필은 기본 속도 방 기준이다.
  게임 코드에서 `Time.timeScale`을 직접 바꾸는 곳은 개발자용 `UI/GMWindow` 하나뿐이다.
- 애니메이터 속도만 바꾸고 `timeScale`은 두는 다른 배속 모드도 감지하지 못한다.
