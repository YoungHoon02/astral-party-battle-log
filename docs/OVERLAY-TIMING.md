# 오버레이 연출 동기화

서버는 봇 행동을 화면 재생보다 먼저 보낼 수 있다. 오버레이는 받은 순서를 유지하면서
연출 길이를 누적해 화면 표시 시점을 추정한다. 파일 로그는 수신 시각에 기록한다.

> **검증 상태:** 순차 재생 하네스와 Release 빌드는 통과했다. 새 빌드의 실게임 표시
> 시점은 아직 검증하지 않았다. 아래 측정 1~3은 모델을 만들 때의 관측 기록이다.

## 원칙

**늦추는 것은 오버레이 출력뿐이다.**

```
패킷 수신 → 프레임 재조립 → 즉시 해석 → 로거 상태 즉시 갱신 → 줄 생성
    ├─ battle-log.txt : 지금 기록 (시각·순서 그대로)
    └─ OverlaySchedule : 예약 → 연출 시점에 LogOverlay로
```

해석이나 상태 갱신을 늦추면 안 되는 이유:

- 턴 주인·원인 문맥(`_turnOwner`, `_said*`)이 다음 패킷과 뒤섞인다
- 골드 송금 짝 맞추기(600ms 보류)가 깨진다
- 소켓 스레드가 기다리게 된다

600ms 골드 보류는 **문장을 만들기 위한 것**이고 표시 예약은 **화면에 내보내기 위한
것**이다. 섞지 않는다 — 보류됐던 줄은 원래 패킷의 종류·그룹을 들고 예약 큐에 들어간다.

## 구성

| 위치 | 역할 |
| --- | --- |
| `Log/LineKind.cs` | 사건 종류 |
| `Log/BattleLogger.cs` | 패킷마다 종류·그룹을 정하고 줄에 붙여 넘긴다 |
| `UI/OverlaySchedule.cs` | 사건을 순서대로 예약하고 동기화 지점을 반영한다. Unity에 의존하지 않는다 |
| `UI/FramePump.cs` | 매 프레임 시계·배속을 넘기고 기한이 된 줄을 꺼낸다 |
| `UI/LogOverlay.cs` | 기존 그대로 그린다 |

소켓 스레드는 `OverlaySchedule.Line/Advance/Page/Reset/Sync`로 넣기만 한다. Unity 객체에 손대지
않고, 기다리지 않고, 디스크에 쓰지 않는다.

### 파일 기록도 소켓 스레드에서 뺐다

전에는 `BattleLogger`가 줄마다 소켓 스레드에서 `File.AppendAllText`를 불렀다. 디스크가
잠깐 막히면 그만큼 다음 패킷 처리가 밀린다(AnimSpeedMod에서 설정 파일 쓰기가 최악 46ms를
막은 기록이 있다). 이제 `Log/LogFileWriter.cs`의 전용 스레드가 쓴다.

- **시각은 넣을 때 찍는다.** 해석 시점의 `HH:mm:ss.fff`라 파일 내용·순서·시각은 전과 같다.
- 새 판의 파일 비우기도 같은 큐를 타서 줄과 순서가 섞이지 않는다.
- 큐(2만 줄)가 차면 그 줄은 버리고 경고를 한 번 남긴다 — 소켓 스레드를 막지 않는 쪽을 골랐다.
- 플러그인 언로드와 프로세스 종료(`AppDomain.ProcessExit`, 순수 .NET 이벤트)에서 남은 줄을
  최대 1초 기다려 쓴다.

## 시계

**프레임 시계**를 쓴다. 매 프레임 `Time.unscaledDeltaTime`을 더하되
`Time.maximumDeltaTime`으로 자른다.

- 게임 연출은 Unity가 잘라낸 `deltaTime`으로 진행한다. 3초 끊김이 있어도 연출은
  0.333초만 나아간다. 실시간 시계를 쓰면 끊김 뒤에 로그가 연출보다 먼저 한꺼번에 풀린다.
- 창이 멈춰 프레임이 안 돌면 시계도 멈춘다. 연출도 멈추므로 맞다.
- Unity 값을 못 읽으면 `Stopwatch`로 대신 흐른다. 시계가 멈추면 로그가 영영 안 나오므로
  배속 연동 실패가 전투 로그 실패로 번지지 않게 한다.

수신 시각은 소켓 스레드가 이 시계를 `Volatile.Read`로 읽어 찍는다. 해상도는 한 프레임이다.

## 배속

**`Time.timeScale`을 읽는다.** AnimSpeedMod(`AstralPartyAnimSpeedMod/Plugin.cs`
`OnFrameTick`)가 배속을 바로 이 값에 쓴다:

```csharp
if (SpeedsDiffer(Time.timeScale, target)) Time.timeScale = target;
```

그래서 다른 모드의 내부 필드를 리플렉션할 필요가 없다. 모드가 없으면 1이고, 배속 제외
씬에서는 AnimSpeedMod가 1로 되돌린다. **게임 자체의 방 속도 설정은 이 값에 드러나지
않는다** — [알려진 한계](#알려진-한계).

- `Time.deltaTime`에서 역산하지 않는다 — 프레임 저하와 배속을 구분할 수 없다.
- 유한하고 0.25~10 사이가 아니면 1로 본다. 이 범위는 측정값이 아니라 안전장치다
  (AnimSpeedMod 배속 목록은 1·1.5·2·3·5). 게임 자체 연출도 `timeScale`을 바꿀 수 있다.
- **줄을 넣을 때의 배속**으로 연출 길이를 환산한다. 기다리는 도중 배속이 바뀌어도
  기존 예약은 다시 계산하지 않는다.

## 순차 재생

사건을 받은 순서대로 처리한다. 새 덩어리의 시작 시각은
`max(수신 시각, 이전 덩어리 종료 시각)`이고, 다음 커서는
`시작 시각 + 연출 길이 / 수신 시점 배속`이다. PK 결과 줄은 시작 후 1.94초에
표시하도록 예약한다. 연속된 같은 그룹의 줄은 첫 줄의 표시 기한을 공유하며, 실제 출력은 FIFO로 한다.

`Overlay.SyncMaxLagMs`는 **덩어리 시작 시각**을 `수신 시각 + 설정값` 이하로
제한한다. PK 공개 지연과 FIFO 대기 때문에 각 줄의 실제 표시 시간이 정확히 설정값
이하가 되는 것은 아니다. 대기열이 4096줄을 넘으면 오래된 줄부터 기한을 무시하고 내보낸다.

| 사건 | 1배속 연출 길이 | 코드에서의 처리 |
| --- | ---: | --- |
| 효과카드 | 2.87초 | `UseEffectCardS2C`의 카드 사용 |
| PK 카드 제출 | 2.23초 | `BattleUseCardS2C` |
| PK 전체 | 9.45초 | `BattleS2C` 결과. 결과 줄은 시작 후 1.94초에 표시 |
| 스킬 | 1.92초 | 스킬 사용·스킬 추정 줄 |
| 판 시작 | 18.15초 | 1라운드 페이지 신호 |
| 주사위 | 2.70초 | 칸 수와 무관하다. 아래 참고 |
| 추가 이동 | 칸당 0.30초 | 받은 칸 수에 곱함. 실측 표본 없음 |

결과 줄(`UpdateHeroAttrS2C`)은 카드·스킬·PK 연출을 다시 기다리지 않도록 길이를 0으로
둔다. 땅 원인은 별도 종류로 남기고, PK 피해는 PK 결과와 같은 그룹으로 묶는다.
카드 기록을 꺼도 공개 카드 사용·PK 카드 제출은 출력 없는 예약으로 커서를 진행한다.
이 길이는 봇전 세 판의 관측 20개에 맞춘 **1배속 추정값**이다. 관측에 대한 평균 오차는
1.45초, 최대 오차는 2.77초였다. 한 판을 제외하면 일부 값의 오차가 7~9초로 커져
독립적인 검증값으로 볼 수 없다.

**주사위는 칸 수에 비례하지 않는다.** 길이를 갖는 항목이 주사위 하나뿐인 구간 일곱을 뒤에
직접 실측했다 — 1칸 1266ms · 3칸 1923ms · 5칸 1585ms · 6칸 2556ms · 8칸 2661/2345ms ·
10칸 1535ms. 회귀하면 `1539ms + 76ms×칸`에 R²=0.19로 칸 수는 설명력이 없다. 전에 여기
적혀 있던 "칸당 이동 시간만 측정 3에서 직접 읽었다"는 틀렸다 — 직접 읽었다던 그 값이
유일하게 확실히 틀린 값이었다 — 칸당 300ms는 적은 칸수에서 크게 모자랐고(1칸 300ms 대
실측 1266ms), 많은 칸수에서는 과하게 늦췄다(10칸 3000ms 대 1535ms). 2.70초는 최소제곱이
아니라 관측 일곱을 모두 덮는 하한이다(모자라면 연출보다 먼저 뜨고 남으면 조금 늦을 뿐이라
오차의 대가가 비대칭이다). 표본이 일곱이라 잠정값이다.

추가 이동의 칸당 0.30초는 네 판에서 한 건도 관측되지 않아 옛 값을 그대로 쓴다. 표본이
생기면 주사위처럼 다시 맞춰야 한다.

## 동기화

헤더의 `UPSN`이 0이 아닌 응답 중, 측정에서 화면 단계와 대응한
`TimeWastingS2C`(5308)·`BattleUseCardS2C`(5036)·`BattleChoiceS2C`(5040)만
동기화 신호로 쓴다. 신호 앞에 받은 줄은 표시 기한이 남았어도 내보내고, 이후 사건을
위한 재생 커서를 그 응답의 수신 시각으로 맞춘다. 본문은 읽지 않고 허용목록도
확장하지 않는다. 다른 응답은 동기화하지 않으므로 상황에 따라 화면을 따라잡는 시점이
늦어질 수 있다.

세 신호 모두 재생 커서를 맞추는 데 쓰지만, **연출 길이를 배우는 관측으로는 검증된
"결정 창 열림"(5308, 본문 14바이트)만 쓴다.** 카드 제출 응답처럼 단계 중간에 오는
신호는 그 시점이 연출 사슬의 끝이라는 보장이 없다. 그래서 동기화 항목은 opcode와 본문
길이를 그대로 기록에 싣고, 구분은 분석 쪽(`tools/fit-timing.js`)에서 한다.

### 연출 길이 보정용 계측

결정 창은 사용자가 아니라 게임이 여는 것이라, 그 시각은 "앞선 연출 사슬이 끝난 정확한
시점"이다. 화면도 연출을 차례대로 재생하므로 도착 시각 `t_i`와 참 길이 `d_i`에 대해

```text
끝_i = max(t_i, 끝_{i-1}) + d_i,   끝_마지막 = 동기화 시각
```

이 성립한다. **이 max 때문에 "합 = elapsed - idle"로 접으면 안 된다** — 계측이 재는
idle은 모델이 자기 (틀린) 길이로 계산한 값이라 화면이 실제로 쉰 구간과 다르다. 접어서
풀면 화면이 중간에 쉰 구간에서 식이 어긋난다(3차 측정에서 같은 판의 두 구간이 +4.9초와
-9.7초로 갈렸다).

그래서 `TraceTiming`은 커서를 움직인 항목을 도착 시각과 함께 하나씩(`segitem`) 남기고,
푸는 쪽이 max를 그대로 둔 채 맞춘다. 동기화마다 남는 누계(`synclead`)는 눈으로 훑기 위한
요약이며 푸는 데 쓰지 않는다. 구간 구성을 스케줄러가 직접 남기는 이유는, 바깥에서
`show` 줄로 재구성하면 출력 없는 예약(`Advance`)이 빠지고 그룹 묶음도 흉내 내야 해서
어긋나기 때문이다. PK 결과 공개 지연(1.94초)은 커서를 움직이지 않으므로 이 방법으로는
구할 수 없다.

## 초기화

각 줄은 넣을 때의 **세대**를 들고 있고, 꺼낼 때 현재 세대와 다르면 버린다. 큐를 비우는
것만으로는 이미 꺼내 둔 줄이 경쟁 상태로 남을 수 있어서다.

| 상황 | 호출 | 동작 |
| --- | --- | --- |
| 새 판(StartGame / MatchSuccess / SingleCampaign / 방 변경) | `Reset` | 세대 증가 + **비우기 신호도 큐를 태운다** |
| 전투 씬 이탈 | `Discard` | 세대 증가. 화면은 그대로 — 이미 보인 로그는 결과 화면에서도 볼 수 있다 |
| 플러그인 언로드 | `Discard` | |
| 오버레이 꺼짐(`Overlay.Enabled=false`) | — | 예약 큐에 아무것도 넣지 않는다 |

`Reset`의 비우기를 큐에 태우는 이유: 따로 보내면 메인 스레드가 이미 꺼낸 지난 판 줄이
비우기 **뒤에** 오버레이에 도착할 수 있다. 큐를 타면 FIFO라 지난 판 줄은 항상 비우기
앞에 선다.

**비우기 신호만은 세대가 지나도 버리지 않는다.** 새 판 직후 전투 이탈(`Discard`)이 겹치면
비우기의 세대가 곧바로 낡는데, 버리면 지난 판 페이지가 새 판에 남는다. 비우기는 여러 번
실행돼도 무해하다.

## 측정 현황

아래는 **이전 고정 지연 모델을 조사할 때 남긴 측정 원문**이다. 현재 순차 재생 모델의
설정법이나 검증 결과로 읽지 않는다. 측정 전에 확인한 것:

- **AnimSpeedMod 리포에 연출 시간 측정이 없다.** 기록된 측정은 설정 파일 읽기 지연
  (최악 46ms → 1.3ms) 하나뿐이다.
- **게임 코드에 쓸 만한 상수가 없다.** 연출 대기는 대부분 변수·에셋(타임라인) 값이다.
  `GachaDiceManager._DiceShowTime = 1000`은 **가챠** 주사위라 전투와 무관하다.
- **네트워크 계층에 순차 큐가 없다.** `RPCMsgManager.ReceiveRPCCallStatic`은 패킷마다
  `UniTaskExtensions.Forget(DealOnPushRPCMsg(...))`로 핸들러를 바로 띄운다. 연출 순서는
  각 게임 로직이 알아서 정한다.

### 현재 모델을 검증하는 법

`Diagnostics.TraceTiming = true`로 두고 배속 1에서 화면에 사건이 나타나는 순간 F10을
누른다. `LogOutput.log`의 `[timing] mark speed=1` 시각을 같은 사건의 `frame` 수신
시각과 `show kind=... planned=... waited=... speed=...` 표시 시각에 대응시킨다.
봇 행동이 연속되는 구간, 사용자 결정 창 앞뒤, PK 결과와 피해, 1라운드 시작을 따로
본다. 이후 배속과 방 속도를 바꿔 같은 비교를 반복한다. F10 기록은 종류별 수신 경과를
자동 계산하지 않으므로 이전 모델의 측정 예시를 그대로 적용하면 안 된다.

| 6 | 마법 찻주전자3 → 파루난(봇) | 23:08:34.257 | 4900ms | 교도소장 행동 시작·주사위, 라운드 2 |

**중앙값 4767ms, 범위 2958~7717ms (약 2.6배).** 편차가 커서 고정 지연 하나로는 맞지 않는다.

편차의 주된 원인은 **캐릭터 스킨마다 공격 모션 길이가 달라서**다(플레이어 확인). 다만 같은
마법 찻주전자끼리도 4·5번(약 3초)과 6번(4.9초)이 달라, 방어자 쪽 모션이나 누른 시점의
오차도 섞인 것으로 보인다. 스킨별로 맞추려면 공격자 스킨을 읽어야 하는데, 지금은 `Hero`에서
`HeroId`만 읽는다(손패가 같은 메시지에 있어서). 스킨이 다른 안전한 필드에 있는지는 확인하지 않았다.

그리고 **타격이 보이기 전에 다음 차례의 패킷이 1초 간격으로 계속 도착했다**(4·5번 제외 전부
2~4개). 봇 차례는 서버 타이머로 오고 화면은 PK가 끝나야 넘어간다면, 이 줄들은 `turn`·`dice`
지연을 0으로 두는 한 PK 줄과 함께 풀려 **자기 연출보다 먼저** 보인다. 누적 모델이 필요한지는
측정 2(봇 차례 표시)로 확인한다.

원본: 이 측정의 `LogOutput.log`와 `battle-log.txt`는 리포에 넣지 않는다(참가자 표시명 포함).

**적용: `attack`·`hit` 모두 4767ms (중앙값).** 스킨 편차 때문에 절반쯤은 여전히 먼저 뜨는 것을
감수했다. PK 줄에도 같은 값을 거는 이유는, PK 줄만 먼저 뜨면 ATK·DICE로 피해량이 드러나기
때문이다(공격 시작 표본 433ms는 한 번뿐이라 쓰지 않았다). 배속을 따르는지는 아직 재지 않아
`fixed` 없이 둔다.

### 측정 2 — 봇 차례 표시 (2026-09-17, 기본 속도 방, 1배속, 프로필 없음)

`ActionStartNotifyS2C`(행동 시작)를 받은 뒤 **화면에 그 봇의 차례가 표시되기까지**.
캐릭터 봇 3명 × 2라운드 = F10 6번으로 대응시켰다(몬스터 차례는 재지 않음).

| 라운드 | 봇 | 차례 수신 | 화면 표시 | 지연 | 그 앞에 몰린 것 |
| --- | --- | --- | --- | ---: | --- |
| 1 | 파루난 | 23:13:03.189 | 23:13:06.590 | 3.40초 | 사용자(사이크스)의 이동 |
| 1 | 판다맨 | 23:13:17.194 | 23:13:27.086 | **9.89초** | 파루난 PK(추격·처치) 결과가 **같은 ms**에 도착 |
| 1 | 패드맨 | 23:13:25.198 | 23:13:43.458 | **18.26초** | 판다맨의 카드·주사위·이동·PK 전부 |
| 2 | 파루난 | 23:14:24.277 | 23:14:26.194 | 1.92초 | 사용자 이동 |
| 2 | 판다맨 | 23:14:35.284 | 23:14:40.268 | 4.98초 | 파루난 PK·체크 포인트 |
| 2 | 패드맨 | 23:14:42.288 | 23:14:45.332 | 3.04초 | 판다맨 이동 |

**1라운드에서 지연이 3.4 → 9.9 → 18.3초로 불어난다.** 해석:

- 서버는 봇 행동을 **자기 타이머(약 1초 간격)** 로 보낸다. 화면을 기다리지 않는다.
- 클라이언트는 연출을 **차례대로** 재생한다. 앞 PK가 끝나야 다음 봇 차례가 나온다.
- 그래서 봇끼리 PK가 이어지면 화면이 패킷보다 점점 뒤처진다.
- **사람이 입력하면 따라잡는다.** 사용자는 화면을 보고 주사위를 굴리므로, 그 입력이 오는
  시점에는 연출이 끝나 있다. 2라운드 사용자 주사위(23:14:18.514)는 라운드 시작 패킷보다
  25.3초 늦었고, 그 뒤 2라운드 봇 차례의 지연은 다시 2~5초로 작아졌다.

**결론: "수신 시각 + 종류별 고정 지연" 모델은 봇전에서 맞지 않는다.** 18초 지연은
`SyncMaxDelayMs`(8초)도 넘는다. 측정 1의 PK 지연(4767ms)도 봇 차례가 몰린 뒤라면 같은 이유로
짧다. 필요한 것은 앞 연출이 끝난 시점부터 다음 연출을 세는 **누적 재생 모델**과, 사람 입력을
**동기화 지점**으로 쓰는 것이다(사람 플레이어는 `Player.IsBot`으로 가를 수 있다 — 이미 읽는 필드).

### 측정 3 — 화면 지연과 내 결정 창 (2026-09-17, 봇전, 1배속, 헤더 진단 켬)

사용자는 보니, 봇은 코마치·Z3000·루루. F10은 봇 차례가 화면에 뜰 때(한 번은 실수로 간수 차례).

| 라운드 | 차례 | 수신 | 화면 | 지연 |
| --- | --- | --- | --- | ---: |
| 1 | 코마치 | 23:25:41.929 | 23:25:57.307 | 15.38초 (판 도입 연출 포함) |
| 1 | Z3000 | 23:26:00.976 | 23:26:27.597 | **26.62초** |
| 1 | 루루 | 23:26:13.983 | 23:26:43.115 | **29.13초** |
| 1 | **보니(나)** | 23:26:22.988 | 23:26:59.662 (결정 창 열림) | **36.67초** |
| 1 | 간수 | 23:27:05.342 | 23:27:07.341 | **2.00초** ← 내 입력 직후 |
| 2 | 코마치 | 23:27:18.004 | 23:27:22.760 | 4.76초 |
| 2 | Z3000 | 23:27:22.007 | 23:27:28.684 | 6.68초 |
| 2 | 루루 | 23:27:26.011 | 23:27:35.061 | 9.05초 |

(측정 2와 같은 규칙으로, F10을 차례 순서대로 대응시켰다. 간수 한 번이 수신 뒤 정확히 2.00초로
맞아 순서 대응을 뒷받침한다.)

**지연은 봇·몬스터 차례를 거치며 쌓이고, 내 결정 창이 열리면 0으로 돌아간다.**
1라운드 끝 무렵 36.7초까지 벌어졌다가, 내가 입력한 직후 간수 차례는 2.0초였다.

**내 결정 창은 헤더만으로 잡힌다.** 게임은 결정 창(카드 사용·주사위·PK 카드 등)을 열 때
`OperationTimer.ActionDownTime`이 `TimeWastingC2S(남은 시간)`을 보내고, 닫을 때 `(0)`을 보낸다.
서버 응답 `TimeWastingS2C`(5308)는 우리 요청이라 헤더 `UPSN`이 0이 아니고, 본문 길이가
열림 14바이트(시간+playerId)·닫힘 9바이트(playerId만)로 갈린다. 실측:

```
23:26:59.662 frame cmd=5308 up=42 len=14   ← 결정 창 열림 (내 차례 수신 36.7초 뒤)
23:27:01.171 frame cmd=5308 up=43 len=9    ← 닫힘
23:27:01.172 frame cmd=5056 up=44 len=9    ← 카드 사용 단계 응답
```

`5004`(Heartbeat)는 5초마다 오는 응답이라 동기화 신호가 아니다. PK에서 방어자일 때는
`BattleUseCardS2C`(5036)·`BattleChoiceS2C`(5040) 응답이 `UPSN≠0`으로 왔다(결정 창 알림은 없었다).
PK 진행 프레임(`end=0`)은 조우·양쪽 카드·주사위마다 한 번씩, 결과(`end=1`)까지 약 1초 간격이었다.

차례 사이 화면 시간(다음 차례 표시 − 이전 차례 표시)으로 본 한 차례 길이:

| --- | --- | ---: |
| R2 코마치 | 카드·주사위·7칸·땅 | 5.9초 |
| R2 Z3000 | 카드·주사위·8칸·체크 포인트 | 6.4초 |
| R1 Z3000 | 카드·주사위·9칸·PK·골드 | 15.5초 |
| R1 루루 | 카드·주사위·3칸·카드 제출·PK·골드 | 16.5초 |
| R1 코마치 | 카드·주사위·8칸·PK·주사위·3칸·PK·골드·이벤트 | 30.3초 |

PK가 끼면 한 차례가 약 10초 늘어난다.

### 다음 단계 — 사람 입력을 동기화 지점으로 (조사 중)

PK·판의 시작·끝 메시지는 있지만(`AskBattleS2C` 5048, `BattleS2C` `isEnd=0/1`,
`GameFinishS2C` 1016) **모두 서버 시각**이라 화면과의 격차를 줄여주지 않는다(측정 2).

화면 쪽 단서는 **사용자의 입력**이다. 주사위·카드 제출 같은 입력은 화면이 그 단계에 왔을
때만 할 수 있다. 서버가 우리 요청에 답한 프레임은 헤더의 `UPSN`이 0이 아니다(게임도 이
값으로 응답을 찾는다, `RPCMsgManager.ReceiveRPCCallStatic`). 헤더 값이라 본문 해석도,
허용목록 변경도 필요 없다.

`TraceTiming`을 켜면 이제 이런 줄이 남는다 (벽시계 시각 포함, 본문은 해석하지 않는다):

```
[timing] 23:13:03.189 frame cmd=1026 ActionStartNotify up=0 down=812 err=0 len=11
[timing] 23:13:17.194 battle id=… end=1 파루난 vs 도둑 pursuit=1 back=0
[timing] 23:13:27.086 mark speed=1 turn=1888ms …
```

(숫자는 형식 예시) 계정 uid는 남기지 않는다 — PK 줄은 표시명을 쓴다.

한 판 돌려서 볼 것: 입력 응답이 어떤 cmd로 오는지(`up≠0`), 그 시각이 화면 따라잡기와
맞는지, PK 한 번에 `end=0` 프레임이 몇 번·어떤 간격으로 오는지.

## 알려진 한계

- 연출 길이는 관측 20개로 맞춘 값이다. 다른 캐릭터 모션, 배속, PvP에서의 오차는 확인하지
  않았다. 측정 1~3은 학습 자료이므로 별도 판으로 다시 검증해야 한다.
- PK 결과와 피해 사이에 다른 출력 줄이 끼면 FIFO 출력 순서 때문에 피해 줄이 PK 결과와
  동시에 나오지 않는다. 측정 3의 PK 결과 다섯 건은 다음 프레임이 모두 능력치 갱신이었다.
- 동기화는 실측한 세 응답에 한정한다. 다른 입력 단계에서는 화면을 따라잡았어도
  재생 커서가 늦게 갱신될 수 있다.
- `SyncMaxLagMs`는 덩어리의 **시작**만 제한한다. PK 공개 지연과 FIFO 대기까지 포함한
  각 줄의 최종 표시 지연을 보장하지 않는다.
- 게임이 `timeScale`을 1보다 작게 낮추는 연출이 있다면 수신 시점의 배속으로 예약하므로
  이후 배속 변화에 맞춰 재계산되지 않는다.
- 게임이 `timeScale = 0`으로 멈추는 일이 있으면 프레임 시계는 계속 흐르므로 그동안
  줄이 먼저 풀린다. 온라인 게임이라 없을 것으로 보지만 확인하지 않았다.
- **게임 자체의 방 속도 설정은 반영하지 않는다.** 게임은 `timeScale`을 쓰지 않고
  `Room.SpeedType`(필드 40)으로 설정표(`ChoosingTimeLimit` gamespeed)를 찾아
  `AnimSpeed`/`DiceSpeed`/`PerformSpeed`/`VfxSpeed`를 분야별로 따로 적용한다
  (`GameLogic/BattleConfig`). 빠른 방에서는 연출이 빨라지는데 여기서는 1배속으로 계산하므로
  **로그가 연출보다 늦게** 뜰 수 있다. 필요해지면 위 필드와 설정표를 읽어 종류별 배율로
  곱해야 한다. 현재 연출 길이는 기본 속도 방 기준이다.
  게임 코드에서 `Time.timeScale`을 직접 바꾸는 곳은 개발자용 `UI/GMWindow` 하나뿐이다.
- 애니메이터 속도만 바꾸고 `timeScale`은 두는 다른 배속 모드도 감지하지 못한다.
