# 게임 처리 대기열로 공개 시점 맞추기 (설계)

상태: 설계 확정(2026-11-07). 실현성 확인 1판을 반영했다. 구현 계획은 [QUEUE-SYNC-PLAN.md](QUEUE-SYNC-PLAN.md).

## 왜 하는가

- 이 모드는 패킷이 도착한 순간 줄을 만들고, 게임은 그 뒤에 연출을 재생한다. 받은 즉시 보여 주면 PvP에서
  결과를 화면보다 먼저 아는 정보 우위가 된다. 이 모드는 PvP에서도 쓰는 것이 전제라서, 해법은 기능을 끄는
  것이 아니라 **화면보다 먼저 보이지 않게 보장하는 것**이다.
- 지금은 연출 길이 모델([OVERLAY-TIMING.md](OVERLAY-TIMING.md))과 화면 신호 게이트
  ([SIGNAL-GATING.md](SIGNAL-GATING.md))로 공개 시점을 추정한다. 연출 이름·배속·관전 같은 조건이 바뀌면 다시
  확인해야 하고, 화면 신호가 없는 줄(몬스터 주사위 등)은 다음 신호나 60초 상한을 기다려야 공개된다.
- 게임은 서버 메시지를 대기열(`RPCMsgManager._OnPushRPCMsg`)에 쌓고, 맨 앞 메시지의 처리기를 끝까지 기다린 뒤
  다음 메시지를 꺼낸다(`ProcessNextPushRPCMsg`). 처리기가 자기 연출을 기다리므로 **대기열 맨 앞이 곧 화면의 진행
  위치**다.
- 대기열 항목은 패킷 헤더의 메시지 종류(`CMDID`)와 순번(`DOWNSN`)을 그대로 갖고 있고, 모드도 같은 값을 헤더에서
  읽는다. 모드가 받는 순서와 게임이 대기열에 넣는 순서가 같으므로, 맨 앞 항목이 모드가 받은 메시지 가운데
  몇 번째인지 찾으면 줄마다 게임이 그 메시지를 처리하기 시작했는지와 끝냈는지 알 수 있다.

## 실현성 확인 (2026-11-07)

가을 환상 숲 연습(봇 3명) 4라운드. 라이브 브리지 watch 네 개를 50ms 간격으로 돌렸다: 맨 앞 `CMDID`·`DOWNSN`,
`_size`, `_version`.

- **대기열은 연출 동안 메시지를 붙든다.** 맨 앞에 머문 시간은 PK 결과(1007) 2.7~7.5초(중앙 5.0),
  주사위(5022) 0.4~1.7초(중앙 1.6), 걷기(5028) 0.15~2.05초, 효과 카드(5056) 1.35~1.91초, 라운드 시작(1015)
  0.7~2.0초였다. 봇 차례에는 최대 75개가 쌓였다. 화면이 서버보다 수십 초 뒤처질 수 있다는 뜻이다.
- **`DOWNSN`은 도착 순서대로 늘지 않는다.** 맨 앞이 바뀐 252번 가운데 29번 값이 줄었다. 결과 메시지(1007·1040·
  1019)가 바로 앞 메시지보다 1~5 작은 값을 갖는 꼴이다. 그래서 "맨 앞 순번이 N보다 크면 N은 끝났다"는 쓸 수
  없다. 이 판에서 (`CMDID`, `DOWNSN`) 쌍은 한 번도 겹치지 않았다.
- 차례 시작(1026)은 맨 앞에 0.05초만 머물렀다. 처리기가 "X의 차례" 배너를 기다리지 않는다.
- 판을 나가면(항복) 대기열이 비워진다(55개 → 0, `ClearRPCMsgData`).
- 디컴파일 확인: `EnqueueOnPushRPCMsg`는 목록 끝에 붙이기만 하고 처리는 늘 [0]부터 한다. 전투 중 수신
  (`NetManager.NetUpdate` → `ReceiveRPC` → `ReceiveRPCCallStatic`)부터 대기열까지 거르는 곳이 없다. 대기열에 들어가지
  않는 것은 즉시 처리 9종, 재연결 동기화 중에 받은 메시지(`_ReconnectCacheRPCMsg`), 소켓을 닫은 뒤 받은 프레임이다.
  요청 응답(UPSN ≠ 0)도 같은 대기열로 들어간다.
- 모드는 소켓 수신 콜백(`EndReceive` Postfix, IO 스레드)에서 프레임을 보고, 게임은 같은 콜백에서 수신 큐에 넣은 뒤
  다음 `NetManager.Update`(메인 스레드)에서 같은 순서로 대기열에 넣는다.
- 게임이 대기열을 통째로 비우는 곳(`ClearRPCMsgData`)은 재연결(하트비트 시간 초과·오류 코드로 소켓을 닫을 때, 새 연결
  성공 때), 판 이탈(항복), 관전 종료다. 하트비트 시간 초과 경로는 소켓을 닫고 대기열을 비우는 일을 메인 스레드의 한
  호출 안에서 하므로, 모드가 소켓 끊김을 알아채기 전에 빈 목록이 보일 수 있다.
- 처리기가 자기 연출을 기다리는 것을 디컴파일로 확인한 메시지: PK 결과(1007, `PlayBattleResult`), 주사위(5022),
  효과 카드(5056), 땅 버프(1013), 라운드 시작(1015). 이동 효과(1096) 처리기는 효과를 저장만 하고, 실제 표시는 뒤따르는
  걷기(5028)가 칸마다 한다. 추가 이동(5044) 처리기는 카메라 전환을 기다린 뒤 주사위를 띄운다.

## 목표

1. **1단계(관찰):** 모드가 대기열 맨 앞을 직접 읽고, 줄마다 기준 메시지의 처리 구간을 기록한다. 공개 동작은
   바꾸지 않는다. 기록으로 다음을 잰다. 추적이 실제로 맞는지, 지금 방식이 처리 시작보다 먼저 보여 준 줄이
   몇 개인지, 화면 신호가 처리 구간 안에 드는지.
2. **2단계(적용):** 줄을 기준 메시지의 처리 구간 [시작, 끝]에 맞춰 공개한다. 처리 시작 전에는 공개하지 않고,
   화면 신호를 놓친 줄도 늦어도 처리 끝에는 공개한다.

## 하지 않는 것

- 대기열 맨 앞 항목의 `CMDID`·`DOWNSN`과 목록 길이 밖의 값은 읽지 않는다. 항목 본문(`PARAM`)도 읽지 않는다.
- 게임 콜백에 붙거나 게임 상태를 바꾸지 않는다([ARCHITECTURE.md](ARCHITECTURE.md) "절대 하면 안 되는 것").
- PvP에서 기능을 끄지 않는다.
- 1단계에서는 공개 동작을 바꾸지 않는다.

## 실패로 보는 것

- 화면보다 먼저 공개되는 줄이 생기면, 다른 점이 나아져도 실패다.
- 게임 크래시나 눈에 띄는 프레임 끊김.
- 허용목록 밖의 값을 읽을 수 있는 코드 경로가 생기는 것. [CONTRIBUTING.md](../CONTRIBUTING.md) 1절의 "코드를
  읽으면 안전이 증명된다"가 깨진다.

## 제약

- 핫업데이트 메모리 읽기는 2026-10-11에 "감사할 수 있는 필드 허용목록부터"라는 조건으로 보류했다. 이 설계가 그
  조건을 맞추고 보류를 푼다(2026-11-07 사용자 결정).
- IL2CPP 쪽에 타입이나 델리게이트를 등록하지 않는다. Il2CppInterop의 `IL2CPP.il2cpp_*` 함수로 필드 값만 읽는다.
  래퍼 객체·메서드 호출(`get_inst()`, `get_Item`)·`il2cpp_field_get_value_object`(읽을 때마다 할당)는 쓰지 않는다.
- 매 프레임 진입점은 `UI/FramePump.cs`(`Time.deltaTime` getter Postfix) 하나다. Harmony 패치를 새로 걸지 않는다.
- 하네스(`tools/harness`)는 BepInEx.Core만 참조한다. IL2CPP를 부르는 읽기 코드와 판단 코드를 파일로 나눠, 판단
  코드만 하네스에 링크한다.

## 읽는 경로

```
Core.Net.NetManager::_inst.RPC._OnPushRPCMsg  →  _items[0].<CMDID>k__BackingField
                                                 _items[0].<DOWNSN>k__BackingField
                                                 _size
```

| 단계 | 내용 | 시작할 때 확인 |
|---|---|---|
| `_inst` | `NetManager`의 부모 `Tools.MonoSingletonProvider<NetManager>`의 정적 필드. 부모를 따라 올라가며 찾는다 | static(0x10)이고 literal(0x40)이 아님. 필드 타입의 클래스가 `NetManager` |
| `RPC` | `NetManager`의 public 인스턴스 필드 | 필드 타입의 클래스가 `RPCMsgManager` |
| `_OnPushRPCMsg` | `List<OnPushRPCMsgData>`, private readonly | 타입 코드 GENERICINST(0x15) |
| `_items`, `_size` | 위 `List` 인스턴스화 클래스의 필드 | SZARRAY(0x1D), I4(0x08) |
| `<CMDID>k__BackingField` | `OnPushRPCMsgData`의 자동 속성 | I4 |
| `<DOWNSN>k__BackingField` | 〃 | I8 |

- 클래스는 도메인의 어셈블리를 돌며 `il2cpp_class_from_name`으로 찾는다. 로그인 전에는 핫업데이트 어셈블리가 없으니
  60프레임마다 다시 찾는다. 찾았는데 필드가 없거나 타입이 다르면 게임이 바뀐 것이라 이번 실행 동안 끈다.
- 오프셋은 시작할 때 한 번 구해 두고, 프레임마다 포인터만 따라간다. `_inst`는 `il2cpp_field_static_get_value`로
  읽되, 그 클래스의 초기화가 끝난 뒤에만 읽는다.
- `RPC`는 재연결 때 새 객체로 바뀐다. 객체 포인터는 프레임을 넘겨 캐시하지 않는다.
- 0 ≤ `_size` ≤ 배열 길이를 확인한다. 처음 보는 객체는 클래스가 맞는지(`il2cpp_object_get_class`) 확인한다. 하나라도
  어긋나면 그 프레임은 "못 읽음"이다.
- 읽기 중 예외가 나면 이번 실행 동안 끄고 지금 방식으로 돈다. AccessViolation은 .NET 6에서 잡히지 않는다. 진짜 방어는
  메타데이터로 확인한 필드 타입과 오프셋만 따라가는 것이다. 클래스 비교는 레이아웃이 바뀐 것을 알아채는 장치일 뿐,
  잘못된 포인터를 막아 주지는 못한다.
- 이 경로들은 astral-party-modding 스킬의 `manifest.json`·`game-paths.md`에 넣어 게임 업데이트 점검에 포함한다.

## 처리 추적

**도착 기록.** 모드는 받은 프레임 가운데 즉시 처리 9종을 뺀 모든 프레임에 도착 번호(1부터 1씩)를 매기고
(번호, `CMDID`, `DOWNSN`, 도착 프레임)을 대기 목록 끝에 붙인다. 허용목록 밖 메시지(걷기 5028 등)도 헤더만으로
기록한다. 본문은 보지 않는다.

- 즉시 처리 9종: 하트비트 5004, 채팅 5096, 맵 표시 5238, 방 동기화 5008, 방 짧은 채팅 5150, 이름 변경 5246,
  영웅 정보 5328, 강퇴 1001, 퇴장 5012.
- 도착 시점은 모드의 펌프 번호(틱)로 찍는다. 틱은 `FramePump`가 실제로 돈 프레임마다 1씩 는다. Unity 프레임 번호는
  펌프가 건너뛴 프레임만큼 뛰어서 여유 계산을 틀리게 만든다(IO 스레드에서 Unity API를 부르지도 않는다).

**펌프마다 맞추기.** 메인 스레드에서 맨 앞 (`CMDID`, `DOWNSN`)을 읽고, 대기 목록 앞에서부터 같은 쌍을 찾는다.

- 찾으면 그 앞 항목은 모두 처리가 끝났고, 찾은 항목은 처리 중이다.
- 목록이 6틱 연속 비어 있으면, 도착한 지 3틱 이상 지난 항목은 모두 끝났다. 틱 k 전에 받은 메시지는 늦어도 틱 k+2가
  돈 프레임의 다음 `NetManager.Update`에서 대기열에 들어가므로 3틱이면 충분하다. 6틱 연속을 요구하는 것은 하트비트
  시간 초과로 게임이 대기열을 비운 경우, IO 스레드의 소켓 끊김 신호가 먼저 도착하게 하려는 것이다. 기다릴 연출이 없는
  처리기는 같은 프레임 안에 들어갔다 빠지므로 맨 앞에서 보이지 않는다.
- 같은 쌍이 둘이면 앞 것과 맞춘다. 틀려도 늦어질 뿐 빨라지지 않는다.
- 맨 앞이 대기 목록에 없으면 "어긋남"이다(아래 추적 상태).

**결과.** 처리는 맨 앞부터이므로 상태는 두 수로 요약된다.

- 시작 경계: 처리를 시작한 가장 뒤의 도착 번호. 번호 R의 메시지는 R ≤ 시작 경계이면 처리가 시작됐다.
- 끝 경계: 처리가 끝난 가장 뒤의 도착 번호. R ≤ 끝 경계이면 처리가 끝났다.

**걷기로 드러나는 메시지의 끝 기준.** 아래 메시지는 처리 끝이 아니라 뒤따르는 걷기(5028)의 처리 끝을 끝 기준으로 한다.

| 메시지 | 이유 |
|---|---|
| 주사위 5022 | 방 속도 2에서는 몬스터 주사위 연출을 건너뛰어(BattleLogic.cs:2460) 눈이 걷기로만 드러난다 |
| 이동 효과 1096 | 처리기는 효과를 저장만 하고, 걷기가 칸마다 효과를 보여 준다(CharacterMove.cs:608) |
| 추가 이동 5044 | 처리기는 카메라 전환 뒤 주사위를 띄우고, 이동량은 걷기로 드러난다 |

5028이 오기 전에 경계 메시지(5022, 차례 시작 1026, PK 결과 1007, 라운드 전환 1117, 라운드 시작 1015, 게임 종료 1016)가
오면 그 메시지 자신이 끝 기준이다. 5022와 5028 사이에는 이동 효과(1096)·예측(1002)·이동 버프(1019)가 끼일 수 있다(실측).
열린 메시지가 여럿이면(5022 뒤 1096) 같은 5028이 모두를 닫는다. 1단계 결과로 신호가 처리 끝보다 늦게 나온 게이트
종류가 있으면 이 표에 뒤 메시지를 더한다(예: 라운드 전환 1117 → 다음 라운드 시작 1015). 1단계에서 늦은 신호가 나온
종류는 차례뿐이었고, 뒤 메시지가 한 가지로 정해지지 않아 더하지 않았다("1단계 결과"의 차례 신호 결정).

**추적 상태.**

| 상태 | 뜻 | 스케줄러가 쓰는 경계 |
|---|---|---|
| 꺼짐 | 시작 직후 아직 맞춘 적 없음, 설정으로 끔, 읽기 영구 실패 | 쓰지 않음(지금 방식) |
| 맞음 | 맨 앞이 대기 목록과 맞음 | 현재 경계 |
| 멈춤 | 새 사실을 믿을 수 없음 | 멈춘 순간의 경계 그대로 |

| 바뀜 | 조건 |
|---|---|
| → 맞음 | 맨 앞이 대기 목록의 항목과 맞음, 또는 6틱 연속 빈 목록. 재연결 신호가 걸려 있으면 그 신호 뒤에 도착한 항목과 맞아야 하고, 빈 목록으로는 풀리지 않는다 |
| 맞음 → 멈춤 | 어긋남, 그 프레임을 못 읽음, 재연결 신호 |
| → 꺼짐(이번 실행) | 필드가 없거나 타입이 다름, 읽기 예외 |

- 재연결 신호와 기준점:
  - 방 동기화(5008)·퇴장(5012) 수신, `ERR`가 0이 아닌 프레임: 그때까지 받은 마지막 도착 번호가 기준점이다.
  - 게임 프레임을 낸 소켓의 끊김: 다음 5008이 올 때까지 기준점이 없다(어떤 항목과 맞아도 풀리지 않는다). 재연결 중에는
    게임이 방 상태를 NONE으로 두고 전투 메시지를 화면 없이 흘려보내기 때문이다(OnlineLogic.cs:371). 5008이 오면 그때의
    마지막 도착 번호가 기준점이 된다.
- 멈춤 동안에도 대기 목록과 경계는 안에서 계속 갱신하지만, 스케줄러에는 멈춘 순간의 경계를 낸다. 낡은 경계는 늦을 뿐
  빠르지 않다. 다시 맞음이 되면 현재 경계를 낸다.
- 재연결 표시(`connectRoomId`)를 허용목록에 더하지 않으려고 헤더와 소켓으로 대신한다.
- 남는 위험: 게임이 대기열을 비울 때 처리 중이던 처리기가 끝나면 그 처리기는 맨 앞에 있는 다른 항목을 지운다
  (`ProcessNextPushRPCMsg`의 `RemoveAt(0)`). 재연결이 연출 도중에 일어나면 다시 들어온 첫 항목 하나가 연출보다 먼저
  끝난 것으로 보일 수 있다.

## 1단계: 관찰

공개 동작은 그대로 두고, 읽기·추적·기록만 넣는다. 측정은 사용자 없이 Claude가 computer-use로 게임을 조작한다
(2026-11-07 목표 지시). 라이브 브리지는 쓰지 않는다. 모드가 매 프레임 직접 읽으므로 시계 맞춤이 필요 없다.

### 기록 (`Diagnostics.TraceTiming`이 켜져 있을 때)

- 기존 `[timing] … frame …` 줄에 `seq=<도착 번호>`(즉시 처리면 `seq=-`)와 `grp=<그룹 번호>`를 붙인다.
- 맨 앞이 바뀔 때 `[timing] … queue head seq=<번호> cmd=<c> down=<d> size=<n> f=<프레임>`.
- 목록이 비면서 항목을 끝낼 때 `[timing] … queue empty done=<끝 경계> f=<프레임>`.
- 어긋날 때 `[timing] … queue unmatched cmd=<c> down=<d> size=<n> f=<프레임>`(같은 맨 앞이면 한 번만).
- 상태가 바뀔 때 `[timing] … queue state=<off|live|frozen> why=<사유> f=<프레임>`.
- 걷기 끝 기준이 정해질 때 `[timing] … queue link seq=<열린 메시지> end=<끝 기준> f=<프레임>`.
- 기존 `show …`·`gate release …` 줄에 `grp=<그룹>`·`ref=<기준 도착 번호>`·`why=<공개 사유>`를 붙인다.
- `f=`는 사람이 읽기 위한 Unity 프레임 번호다. 분석은 줄 앞의 벽시계 시각을 쓴다.

### 절차

1. 빌드를 배치하고 BattleLog 설정에서 `Diagnostics.TraceTiming`을 켠다. AnimSpeed 같은 연출 속도 모드가 깔려
   있으면 그 설정을 기록에 적는다.
2. 연습 모드 협동 챌린지 맵(아무거나)에서 3~4라운드를 진행하고 항복한다. 1배속으로 2판. 이 PC의 AnimSpeed는 전투
   씬을 제외 목록에 두고 있어 전투가 1배속이다. 다른 모드의 설정을 바꾸지 않으려고 다른 배속 판은 하지 않는다.
   공개 규칙은 연출 길이를 쓰지 않으므로 배속에 따라 달라지지 않는다.
3. `tools/probe_queue.py`에 `BepInEx/LogOutput.log`를 넣는다.

### 분석 (`tools/probe_queue.py`)

- **추적:** 맨 앞 변화 수, 어긋남 수와 그때의 cmd, 맞음 상태였던 전투 시간 비율, 상태 바뀜 사유별 수.
- **메시지마다:** 도착 시각, 처리 시작, 처리 끝, (처리 시작 − 도착) 대기. 종류(cmd)별로 머문 시간 분포.
- **줄마다:** show 시각을 그 줄 기준 메시지의 [처리 시작, 처리 끝]과 비교한다.
  - 처리 시작보다 0.1초 넘게 이른 줄: 지금 방식이 먼저 보여 준 줄이다. 종류별 수와 최대값.
  - 화면 신호로 공개된 게이트 줄: show(신호 시각)가 [처리 시작 − 0.1초, 끝 기준의 처리 끝 + 0.1초] 안에 드는지.
    게이트 종류(주사위·PK·라운드·차례)별로 센다.
  - 결과 줄(1040·1013·1096·5044, 끝 기준은 위 표): (처리 끝 − show) 분포. 2단계에서 얼마나 늦어지는지다.
  - 결과 줄 가운데 처리 끝보다 이른 줄: cmd별 수와 최대값. PK 원인 1040의 나머지 줄(골드·버프 등)은 로거가 그 1040의
    그룹으로 내므로 여기에 들어간다.
- 출력은 사람이 읽는 표 한 장과 종료 코드. 기록 줄이 하나도 없으면 종료 코드 2.

### 2단계로 넘어가는 기준

- 크래시·프레임 끊김이 없다.
- 첫 맞음 이후 전투 시간의 95% 이상이 맞음 상태다. 어긋남이 맨 앞 변화의 1% 이하이고, 어긋남마다 원인을 설명할 수
  있다(재연결·판 이탈 등).
- 화면 신호로 공개된 게이트 줄이 모두 [처리 시작 − 0.1초, 끝 기준의 처리 끝 + 0.1초] 안에 든다. 처리 끝보다 늦은
  신호가 나온 게이트 종류는 신호가 드는 뒤 메시지를 끝 기준 표에 더한다. 처리 시작보다 이른 신호는 지금 방식이 앞
  사건의 신호를 잘못 짝지은 것인지 먼저 본다(2단계는 처리 중인 메시지의 신호만 받는다). 같은 메시지의 화면 사건이
  처리 시작보다 앞선 것이라면 "맨 앞이 화면 위치"라는 전제가 깨진 것이라 2단계를 멈추고 원인을 찾는다.

## 2단계: 공개 규칙

규칙은 화면 동기화(`SyncWithAnimation`)와 새 설정 `QueueSync`가 둘 다 켜져 있을 때, 추적이 맞음이거나 멈춘 지 60초가
안 됐으면 쓴다(이하 "대기열 규칙 적용 중"). 멈춘 시간은 스케줄러 시계로 멈춤을 처음 본 펌프부터 센다. 그 밖에는 지금
방식(모델·화면 신호·60초 상한) 그대로다. 화면 신호 후킹이 실패해 모델 경로로 돌아간 경우에도 규칙을 쓴다(아래 7).

### 줄마다 기준이 되는 메시지

줄은 자기 그룹을 연 프레임의 도착 번호를 기준으로 갖는다. 로거는 프레임마다 그룹을 하나씩 만들고, 보류했다가
나중에 내보내는 줄(대상 미상 `UpdateHeroAttr` 보류, 골드 짝 맞추기)도 원래 그룹을 유지한다.

| 줄 | 처리 시작의 기준 | 처리 끝의 기준 |
|---|---|---|
| 기본 | 그룹을 연 프레임 | 같은 프레임 |
| PK 원인 1040의 체력 줄 | PK 결과(1007) | 같은 프레임 |
| PK 원인 1040의 나머지 줄(골드·스탯·버프·레벨 등) | 그 1040 | 같은 프레임 |
| 주사위 5022·이동 효과 1096·추가 이동 5044 | 그 프레임 | 뒤따르는 걷기(5028), 없으면 그 프레임 |
| "게임 종료" 구분선 | 게임 종료(1016) | 같은 프레임 |
| 기준 없음 | 즉시 처리 9종에서 나온 줄(채팅·맵 표시), 동기화·비우기 항목, 1라운드 페이지 | — |

- PK 화면은 타격 때 피해와 남은 체력을 보여 주지만, 골드·처치·버프·레벨 변화는 PK 연출이 끝난 뒤 그 1040의 처리기
  (`UpdateAllHeroAttr`)가 보여 준다. 그래서 체력 줄만 PK 그룹으로 보내고, 나머지는 자기 1040을 기준으로 둔다. 로거는
  체력 줄을 먼저, 나머지를 뒤에 낸다(앞 줄과 함께 나가는 묶음은 연속한 같은 그룹 줄까지라서).
- "게임 종료" 구분선은 1016 다음에 온 프레임 때 나간다. 그 프레임이 하트비트(즉시 처리)여도 기준을 잃지 않게 1016의
  그룹으로 낸다.
- 1라운드 페이지는 전투 씬 로드 전에 와서 오버레이 표시 판단에 쓰이므로 하한을 걸지 않는다.

### 규칙

1. **하한:** 기준이 있는 줄은 기준 메시지의 처리가 시작되기 전에는 내보내지 않는다. 모델 기한·늦은 경로·상한 모두에
   걸린다. 예외는 대기 줄이 4096개를 넘는 비상 배출(지금과 같다)뿐이다.
2. **게이트 줄(주사위·PK·라운드·차례)의 신호:** 화면 신호는 지금 처리 중인 게이트 줄(처리 시작 ≤ 지금 < 끝 기준의
   처리 끝)에만 짝짓는다. 처리 전이나 끝난 줄을 위한 신호는 버린다. PK 결과 연출은 1007 처리기 안에서 돌기 때문에,
   1007이 시작되기 전에 본 타격은 그 PK의 타격일 수 없다. 이 동안에는 장부(늦게 온 신호를 다음 줄 대신 소비하는 기록),
   앞 줄 늦은 해결(`ResolveOlder`·`PkStarted`)을 쓰지 않는다.
   - "처리 중"은 신호를 보기 직전 펌프의 경계로 판단한다. 펌프 사이에 본 신호는 그 펌프가 맨 앞을 읽은 뒤에 났으므로,
     이번 펌프의 경계로 판단하면 같은 프레임에 시작한 다음 PK에 앞 연출의 신호(약한 창 닫힘 등)가 붙을 수 있다.
   - 라운드·차례 줄은 직전 펌프와 이번 펌프 중 어느 쪽에서든 처리 중이면 신호를 받는다. 라운드 팁은 처리기가
     시작되는 프레임에 켜져 직전 펌프 경계로는 늘 놓치고, 두 줄은 판에 이미 보이는 정보만 담는다. 내보내는 데는
     여전히 이번 펌프의 처리 시작이 필요하다(규칙 1).
   - PK 창은 그 창이 열려 있는 동안 처음 처리 중이 된 PK 줄에 묶는다. 창 닫힘(약한 창)은 그 줄만 해결하고, 닫힘을
     놓친 채 새 창이 열려도 앞 창으로는 아무 줄도 해결하지 않는다(규칙 3이 맡는다).
3. **게이트 줄의 신호 놓침:** 끝 기준의 처리가 끝나면 늦은 경로로 해결한다(사유 `QueueEnd`). 장부에 올리지 않는다.
   규칙이 꺼져 있던 동안 정해진 해결(상한·옛 짝짓기·`ResolveOlder`·`PkStarted`)은, 규칙이 다시 적용되면 끝 기준의
   처리가 끝나기 전에는 쓰지 않는다. 60초 넘게 멈췄다가 다시 맞음이 되는 순간 PK 줄이 타격보다 먼저 나가지 않게 하려는 것이다.
4. **게이트 없는 줄:** 결과 줄(그룹을 연 프레임이 1040·1013·1096·5044)은 끝 기준의 처리 끝에, 나머지는 처리 시작에
   내보낸다. 이때 모델 기한, PK 장벽, 반격 동기화는 보지 않는다. 그룹이 같은 줄은 지금처럼 앞 줄과 함께 나간다.
5. **상한:** 대기열 규칙 적용 중에는 기준이 있는 게이트 줄에 60초 상한을 걸지 않는다. 봇전에서 화면이 60초 넘게
   뒤처질 수 있어(최대 75개 대기) 수신부터 세는 상한이 오히려 먼저 공개하기 때문이다. 대신 추적이 60초 넘게 멈추면
   지금 방식으로 돌아가고, 그때 상한이 다시 걸린다.
6. **모델 커서:** 규칙으로 줄을 내보낼 때 그 시각으로 앵커를 세운다. 지금 방식으로 돌아가도 화면 위치에서 다시
   추정한다. 모델 예약은 줄이 맨 앞에 올 때 늘 계산해 둔다.
7. **모델 경로:** 화면 신호 후킹이 없거나 꺼져 모델 경로로 돈 때도 하한을 건다. 주사위·PK 줄과 결과 줄은 끝 기준의
   처리 끝에, 나머지는 처리 시작에 내보낸다.
8. **파일 기록:** `battle-log.txt`의 "미표시" 강제 기록은 줄의 나이가 아니라 펌프가 60초 넘게 돌지 않았을 때만 한다.
   대기열 규칙으로 120초 넘게 기다리는 줄이 오버레이보다 먼저 파일에 쓰이면 안 되기 때문이다.

규칙 4는 "결과 줄만 처리 끝" 결정(아래)의 구현이다.

### 재생과 하네스

- 재생 기록에 세 종류를 더한다(기존 `Mark` 뒤에 붙이고 스케줄러 버전을 올린다).
  - 줄 기준: 항목 번호, 기준 도착 번호, 결과 줄 여부, 걷기 끝 기준 여부. 줄 기록 바로 뒤에 남긴다.
  - 추적 상태: 상태(꺼짐·맞음·멈춤), 시작 경계, 끝 경계. 값이 바뀐 펌프에만 남긴다.
  - 걷기 끝 기준: 열린 메시지의 도착 번호, 정해진 끝 기준 번호.
- 스케줄러는 펌프 첫머리에 추적 상태를 한 번 잡아(스냅숏) 그 펌프 내내 쓰고, 그 값을 기록한다. 하네스는 기록에서
  스냅숏을 되살려 규칙을 게임 없이 재현한다. 추적 판단 코드(맞추기·빈 목록·재연결·끝 기준)는 하네스에서 직접 시험한다.

### 건강 기록과 설정

- 판마다 건강 요약 줄 끝에 대기열 구간을 붙인다: 맞음 비율, 맞춤 수, 어긋남 수, 멈춤 수(사유별), 못 읽은 프레임 수,
  최대 대기 길이, 최대 (처리 시작 − 도착). 기존 구간의 형식(해결 4종)은 바꾸지 않고, `QueueEnd`는 늦은 경로로 센다.
- `[Overlay] QueueSync`(기본 켬). 끄면 읽기 자체를 하지 않는다.

## 2단계 검증 (2026-11-07)

**판 정보.** 1단계와 같은 맵("가을 환상 숲", 연습 모드)에서 1배속으로 2판을 했다(라운드 시작 1015를 1판 8회, 2판 5회
받음, 항복으로 끝냄). 함께 깔린 모드와 설정은 1단계와 같다.

**결과.** 분석 도구 `--expect-queue`의 종료 코드는 0이고, 규칙 위반은 0건이다.

- 맨 앞 변화 1622회 가운데 어긋남은 0회다. 맞음 97.9%, 멈춤 2.1%다. 멈춤은 1판 퇴장 뒤 로비에서 기다린 시간이다.
- 처리 시작보다 이른 줄은 0개다(1단계 지금 방식은 142개). 처리 끝보다 이른 결과 줄도 0개다(1단계 136개).
  결과 줄 244개는 모두 끝 기준의 처리 끝에 나갔다(차이 0.00초).
- 화면 신호 게이트(구간 안/밖): 주사위 49/0, PK 53/0, 라운드 11/0, 차례 91/0.
- 공개 사유: PK 53줄은 모두 화면 신호다(타격 44, 약한 창 닫힘 9). 라운드 11줄도 모두 팁 신호다. 늦은 경로(`queue-end`)는
  주사위 69줄과 차례 20줄이다. 주사위는 눈 없는 몬스터 주사위가 걷기 끝에 나간 것이다.
- 판마다 건강 요약의 대기열 구간:
  - 1판: `queue live=100% frozen=0% matched=82392 unmatched=0 unread=0 overflow=0 freeze=0/0/0/1/0/0 maxsize=127 maxwait=5374t`
  - 2판: `queue live=100% frozen=0% matched=34256 unmatched=0 unread=0 overflow=0 freeze=0/0/0/1/0/0 maxsize=72 maxwait=3161t`
- 판 끝에 나가지 못한 게이트 줄은 2판 0개, 1판 차례 줄 2개다. 이 둘(기준 2021·2023)은 항복 1초 전에 도착했고,
  화면이 2015를 처리하던 중에 게임이 대기열을 비웠다. 게임도 보여 주지 않은 차례라 내보내지 않는 것이 맞다.
- 화면으로 확인: PK 줄과 체력 줄이 1007 처리 시작 1.96초 뒤 타격 신호에 함께 떴다. 화면의 체력 숫자가 바뀌기 직전이다.
- 예외: 게임을 끌 때 소켓 수신 예외가 한 번 남는다. 이 기능 이전부터 있던 것이다. 그 밖의 플러그인 예외·경고는 없다.

**측정 중 알게 된 것.** 항복 확인은 게임이 대기열의 메시지를 처리하는 중이면 서버로 나가지 않는다. 확인을 눌러도 메뉴로
돌아올 뿐이다. 봇전에서는 내 결정 차례처럼 화면이 서버를 따라잡아 대기열이 빈 순간에 눌러야 한다.

## 일반 줄 처리 방식

**결정(2026-11-07, 작성자):** 사용자가 결정에 참여하지 않고 릴리스 가능한 구현까지 진행하라고 지시해서, 작성자가
**결과 줄만 처리 끝(2안)**으로 정한다.

- PvP에서 정보 우위가 되는 것은 결과(체력·골드·버프 변화)다. 결과 줄은 처리 끝에 내보내 보장을 지킨다.
- 카드·스킬 사용 줄은 처리가 시작되는 순간, 즉 게임이 그 행동을 보여 주기 시작하는 순간에 낸다.
- 늦어짐은 결과 줄의 처리 시간에만 생긴다(실측 1040 중앙 0.81초, 최대 3.25초).
- 1단계에서 결과 줄의 늦어짐이 1배속 95%값 3초를 넘으면, 결과를 기록한 뒤 2안을 유지할지 다시 본다.

| 안 | 내용 | 득실 |
|---|---|---|
| 처리 끝 | 모두 처리 끝에 공개 | 보장이 가장 강하다. 대신 카드·스킬 줄이 연출이 끝날 때 뜬다 |
| 결과만 처리 끝 | 결과 줄만 처리 끝, 나머지는 처리 시작 | 늦어짐이 결과 줄에만 생긴다 |
| 모델을 구간 안으로 | 지금 모델 예약을 [처리 시작, 처리 끝]으로 자른다 | 구간 안에서는 모델 추정에 기대므로 보장이 가장 약하다 |

## 고르지 않은 길

| 길 | 고르지 않은 이유 |
|---|---|
| `DOWNSN` 크기 비교로 끝 판정 | 도착 순서대로 늘지 않는다(실측 252번 중 29번 감소) |
| 대기열 전체 순회 | 맨 앞 하나로 충분하다. 읽는 양만 는다 |
| 라이브 브리지로 1단계 측정 | 50ms 표본·시계 맞춤이 필요하다. 모드가 매 프레임 읽으면 둘 다 필요 없다 |
| 차례·라운드 값(`CurPlayerId`, `_Round`) 읽기 | 차례 경계만 알려 주고 줄 단위 시점은 못 준다 |
| `RPCMsgManager` 콜백 후킹 | 게임 처리기를 바꿔 버리고, 델리게이트 등록이 크래시 금지 목록에 걸린다 |
| 재연결 표시를 허용목록에 추가 | 헤더와 소켓으로 알 수 있어서 읽는 경로를 늘릴 이유가 없다 |

## 작성자 판단으로 정한 것

- 끝 판정은 도착 순서 맞추기로 한다(`DOWNSN` 비교를 버린 이유는 실측).
- 1단계 측정은 라이브 브리지 대신 모드 자체 읽기로 한다. 걷기 끝 화면 시각(위치 watch)은 재지 않는다. 걷기(5028)
  처리기가 머문 시간이 경로 길이에 따라 0.15~2.05초로 변해 걷기를 기다린다고 본다.
- 도착 시점은 펌프 틱으로 센다. 빈 목록은 6틱 연속, 도착 뒤 3틱. 맞음 비율 기준 95%, 어긋남 기준 1%, 신호 여유 0.1초.
- 추적 상태는 꺼짐·맞음·멈춤 셋이다. 한 프레임을 못 읽거나 어긋나도 지금 방식으로 바로 돌아가지 않고 마지막 경계를
  붙든다(바로 돌아가면 수신부터 센 60초 상한이 밀린 줄을 한꺼번에 내보낸다). 60초 넘게 멈추면 지금 방식으로 돌아간다.
- 재연결 신호는 방 동기화(5008)·퇴장(5012)·오류 프레임(`ERR` ≠ 0)·소켓 끊김이다. 소켓이 끊기면 다음 5008 뒤에 도착한
  항목과 맞을 때까지 멈춘다.
- 대기열 규칙 적용 중에는 게이트 줄에 60초 상한을 걸지 않고, 신호는 처리 중인 줄에만 짝지으며, 장부를 쓰지 않는다.
- 신호의 "처리 중" 판단은 직전 펌프 경계로 한다(늦는 쪽으로만 틀린다). 라운드·차례 줄만 이번 펌프 경계도 받는다.
  PK 창 닫힘은 그 창에 묶인 PK만 해결한다. 규칙이 꺼진 동안 정한 해결은 다시 적용되면 끝 기준의 처리 끝까지 쓰지 않는다
  (구현 리뷰에서 재현된 두 조기 공개 경로를 막은 것).
- 걷기로 드러나는 메시지(5022·1096·5044)의 끝 기준은 뒤따르는 5028이다. 1096·5044는 결과 줄이다.
- 차례 시작(1026)에는 끝 기준을 더하지 않는다. 1단계에서 차례 신호 3/75건이 처리 끝보다 최대 0.48초 늦었지만, 신호가
  드는 뒤 메시지가 일정하지 않고, 차례 줄에는 판에 이미 보이는 정보만 있다.
- PK 원인 1040은 체력 줄만 PK 타격에 맞추고, 나머지는 자기 처리 끝에 낸다.
- 화면 신호 후킹이 없는 모델 경로에도 대기열 규칙을 쓴다.
- 일반 줄은 2안(결과 줄만 처리 끝)으로 한다.
- 2026-11-07 설계 검토(빌더 검토·반박 검토)에서 나온 지적을 위 결정으로 반영했다.
